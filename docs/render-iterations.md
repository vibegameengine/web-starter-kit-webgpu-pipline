# Итерации развития Webgiya

Актуальная цель: [виртуальные текстуры и единый освещённый мир](render-quality-goal.md). Каждый шаг даёт работающий прирост. Проверка отвечает на вопрос этого шага.

## 01 — Запечённая статика и живые приёмники вместе

**Результат:** `?mode=hybrid` оставляет static lightmap на поверхностях с bake и запускает существующий lifecycle/integrator/resolve Webgiya для движущихся объектов. Нижняя часть шара получает GI. В UI доступен режим hybrid; старые surfel/lightmap остаются для сравнения.

**Что соединено:** bake явно запрашивает сохранение live surfels; закреплённый atlas и свободный хвост пула работают одновременно. Resolve получает состояние закрепления от SurfelGI вместо глобального URL-флага. FrameGraph использует маску конкретного приёмника в alpha существующего MRT, чтобы не добавить полный realtime indirect поверх baked indirect. Дополнительного render target для маски нет.

**Один проверенный риск:** переключили только realtime-вклад в одной неподвижной сцене. 580516 внутренних пикселей запечённых поверхностей остались совершенно одинаковыми; 6200 пикселей незапечённого приёмника изменились. Это проверка отсутствия двойного света, не оценка физической точности или общего FPS. На контрольном кадре закреплено 148480 surfels, живых после перемещения/resize — 15, ошибок браузера — 0.

Команды:

```powershell
npm run dev
node scripts/check-hybrid.mjs
npm run typecheck
npm run build
```

Лично просмотрены свежие headed-кадры [с GI](../shots/hybrid-iteration-01/on.png), [без realtime GI](../shots/hybrid-iteration-01/off.png), [после перемещения](../shots/hybrid-iteration-01/moved.png) и [после resize](../shots/hybrid-iteration-01/resized.png). Typecheck и production build проходят. Существующее предупреждение Inspector о frame scope и предупреждение Vite о размере bundle остаются.

**Границы шага:** это маршрутизация приёмников. Статический indirect пока не меняется от движущегося препятствия; stale-light invalidation не завершена. На движущемся шаре в тени остаётся недостаток пространственной детализации света. Одного этого режима недостаточно для завершения общей цели. Виртуальные страницы, сохранение bake, полноценная дешёвая модель динамики и общие ограничения масштаба ещё впереди.

**Следующий полезный шаг:** подключить страничное чтение готовой lightmap с постоянно доступным грубым fallback; затем загрузку/вытеснение страниц. Не начинать новую кампанию измерений.

## 02 — Замороженная статика по умолчанию и страницы без чёрных дыр

**Дефект:** default `surfel` прогревал покрытие через ракурсы камеры. Полный `frozen` останавливал заполнение пропущенных поверхностей: на внешней красной стене оставался чёрный центр с пятнистым краем. Это не готовая lightmap.

**Результат:** default теперь `hybrid`, полный статический UV-атлас запекается при старте. UI показывает `static frozen` как состояние готовой статики; live GI остаётся для динамических приёмников. Старый полный freeze доступен только в явно выбранном экспериментальном `surfel`. Разделение экрана диагностикой выключено по умолчанию. Неполное заполнение атласа из-за исчерпания пула завершает bake ошибкой вместо публикации заведомо дырявой карты.

**Страницы:** готовая карта читается через ограниченный кеш массива текстур (8 слотов по умолчанию), integer page table, соседние gutters и переход к доступному mip. Грубая карта 128² постоянно доступна. CPU выбирает страницы по видимым треугольникам и их экранной площади; очередь ограничена, upload — максимум 2 страницы за кадр. Одностраничный staging + GPU copy обходят отсутствие частичного upload массива в r182. В r182 explicit-LOD filtered array sampling теряет layer в WGSL, поэтому физический кеш с единственным mip использует implicit sampling с layer; виртуальный LOD выбирается отдельно.

**Проверка задачи пользователя:** `node scripts/check-frozen-static.mjs` открывает default hybrid, поворачивает камеру к внешней красной стене, очищает все детальные страницы и приостанавливает их загрузку, затем возобновляет загрузку и перемещает шар. Лично просмотрены `shots/frozen-static/inside.png`, `outside-fallback.png`, `outside-resident.png`, `outside-moved.png`: чёрной дыры на стене нет даже при 0 резидентных страницах. Произошёл ровно 1 bake; GPU-пиксели готового fallback остались побитно прежними; 148480 статических surfels закреплены. Ошибок браузера нет. Это проверка конкретного дефекта, не заявление о физической точности или производительности всего рендера.

**Границы:** страницы пока загружаются из RAM, исходная полная bake-текстура и пул всё ещё выделены на GPU; общего сокращения памяти пока нет. Bake не сохраняется между перезагрузками страницы. Полноценная фильтрация произвольных UV charts, диск/сеть, освобождение bake-ресурсов и более качественная дешёвая динамика остаются следующими отдельными шагами. В экспериментальном `surfel` полный freeze всё ещё способен заморозить неполное покрытие; он не используется по умолчанию.

Итоговые проверки: `typecheck`, production build и `git diff --check` прошли. Проверка приёмников после подключения страниц также прошла: 580516 внутренних пикселей статики не изменились при отключении realtime GI, 6199 пикселей динамического приёмника изменились; ошибок браузера нет. Предупреждения Inspector и размера production bundle остаются.

## 03 — Повторное использование bake после перезапуска

**Результат:** default hybrid сохраняет bake в `public/bakes/<key>.bin` и краткие метаданные `.json`. При следующем запуске подходящий файл восстанавливает lightmap и закреплённый surfel-кеш без UV raster bake и без интеграционных проходов. Динамика получает прежний свет, radial-depth visibility и обученное распределение направлений через наследование от статических surfels. Восстанавливаются оба буфера моментов, стек свободных слотов и его граница, чтобы динамический allocator не перезаписал статические данные.

**Пригодность файла:** SHA-256 ключ учитывает исходный код, lockfile, статическую геометрию/UV/индексы/инстансы, преобразования, параметры материалов и пиксели diffuse/emissive maps, источники света, environment, blue noise и настройки bake. Камера исключена, кроме явно запрошенного экспериментального `bakecam=view`. Хеш исходников пока консервативный: изменения любого файла в src инвалидируют файл. Формат имеет версию, контроль размеров и SHA-256 checksum. Повреждённый файл отвергается, приложение выполняет и сохраняет новый bake. `re-bake now` явно пересчитывает, даже если файл подходит; `?bakeCache=0` отключает сохранение/загрузку для проверки самого baker.

**Хранение в проекте:** development-only middleware пишет только имена из 64 hex-символов в `public/bakes`, принимает same-origin PUT и публикует файл переименованием временного файла. Данные исключены из HMR: сохранение не должно перезапускать приложение. GET обслуживается явно, потому что Vite иначе не видит новые файлы в исключённой директории. Production build копирует готовые public-артефакты и только читает их. Если сохранить нельзя, рассчитанное освещение продолжает работать, а причина доступна в `__audit.bakeCache()`.

**Исправленная зависимость:** рост GPU-пула раньше создавал integrator с дефолтными env/bounce/albedo настройками. Теперь заданные параметры сохраняются при пересоздании, в том числе при восстановлении bake.

**Проверено:** `node scripts/check-bake-persistence.mjs` запускает отдельные процессы Chrome. Cold: 1 bake и сохранение. Следующий процесс: 0 bake, восстановлены 148480 pinned surfels; GPU-пиксели fallback совпали побитно, 580516 внутренних пикселей статических поверхностей beauty совпали. `sun=0` дал другой ключ и отдельный bake. Искусственно повреждённый файл был отвергнут по checksum и заменён новым расчётом. Ошибок браузера нет. Лично просмотрены свежие headed-кадры `shots/bake-persistence/baked.png`, `loaded.png`, `sun-off.png`, `recovered-outside.png`, `preview.png`.

Typecheck и production build прошли. Production preview также восстановил тот же ключ без bake и ошибок; для повторения после build: запустить `npm run preview -- --port 5190`, затем `$env:BAKE_BASE_URL='http://127.0.0.1:5190'; node scripts/check-bake-persistence.mjs --saved-only`.

**Границы и следующий шаг:** текущий файл Cornell занимает 101597248 байт и загружается целиком. Это точное сохранение существующего состояния, ещё не масштабируемый формат мира. Следующая полезная итерация — сжатые независимо загружаемые страницы и отдельное размещение статического освещения для динамических запросов; текущая пропорция «один runtime surfel на texel» слишком дорога для большого мира. Локальные изменения пока выбирают другой полный bake, не пересчитывают только затронутую область. Дефекты дешёвой модели динамики и прочие требования общей цели остаются открытыми.

## 04 — Сжатые страницы с загрузкой по запросу

**Результат:** при сохранении проекта публикуются `<key>.stream.json` и независимые gzip-ресурсы `blobs/<sha256>.chunk`: fallback, детальные страницы с gutters и четыре массива статического surfel-кеша. Нейтральное расширение существенно: preview-сервер автоматически добавлял Content-Encoding для `.gz`, а браузер тогда распаковывал данные до нашего декодера. Ресурсы именуются по содержимому, проверяются по размеру и checksum, манифест заменяется атомарно после записи всех его данных. Страничный builder общий для RAM-пути и server packing — mip и gutters не реализованы двумя расходящимися алгоритмами.

Default hybrid после перезапуска читает манифест и fallback, восстанавливает нужный текущей модели динамики статический кеш, затем подгружает только затребованные lightmap-страницы. Полная lightmap и CPU mip-цепочка не создаются на этом пути; полный GPU atlas тоже не выделяется. Старый `.bin` остаётся для совместимости и `vt=0`, при наличии корректного манифеста default не запрашивает его. После первоначального авторского bake данные ещё находятся в RAM: переход к HTTP-источнику происходит при следующем восстановлении.

В очереди не более 4 запросов, upload не более 2 страниц за кадр. Смена набора видимых страниц отменяет ненужные запросы. Clear/dispose отменяют запросы; поколение и проверка владельца исключают публикацию запоздалого ответа. Неудачная проверка или загрузка сохраняет fallback, повторы идут через 1/2/4…30 секунд. Gzip распаковывается через DecompressionStream с ограничением выходного размера, после чего проверяется SHA-256. HTTP-кеш может повторно использовать неизменяемые ресурсы.

**Проверка конкретного результата:** `node scripts/check-page-streaming.mjs` создаёт bake, открывает новый Chrome, задерживает все детальные страницы, поворачивает камеру, разрешает загрузку, возвращает камеру, затем подсовывает страницы с неверным checksum и восстанавливает ответы. На маршруте затребовано 11 из 20 уникальных страниц; произошло 3 вытеснения, повторного bake и запросов `.bin` — 0. При задержке и повреждении было 0 резидентных страниц и видимый свет из fallback. После загрузки 580516 внутренних пикселей статики совпали с RAM-путём без отличий. Повреждение не приводит к запросам каждый кадр; автоматическое восстановление проходит. Ошибок браузера нет.

Лично просмотрены свежие headed `shots/stream-pages-before.png`, `shots/stream-pages-first.png`, `shots/page-streaming/outside-delayed.png`, `outside-streamed.png`, `failed-fallback.png`, `recovered.png`. Typecheck, production build и diff check прошли. Production preview с `check-bake-persistence.mjs --saved-only` проверяет именно `storage=streamed`.

**Размер и границы:** все уникальные сжатые данные последнего bake вместе занимают 54938804 байт против 101597248 байт старого bundle; это размеры артефактов, не замер VRAM или фактического сетевого трафика. Четыре surfel-массива всё ещё загружаются целиком и занимают прежний GPU-пул. Сжатие файлов этого не исправляет. Следующий важный шаг — отделить представление света для динамических запросов от числа texels lightmap, сохраняя видимость и пространственные детали. Полноценное взаимодействие динамики со статическим indirect и большие сцены ещё не завершены.

Production preview после исправления расширения подтвердил `source=saved`, `storage=streamed`, 0 bake и 0 ошибок браузера. Свежий `shots/bake-persistence/preview.png` просмотрен: статика освещена, но на нижнем крае динамического шара виден чёрный контур при малом live-покрытии (3 surfels). Это оставшийся дефект динамического GI, не закрытый проверкой статических страниц; его нужно учитывать в следующей итерации модели динамики.

## Итерация 05 — восстановление покрытия динамических поверхностей

**Дефект:** проверка покрытия учитывала pinned-пробы, которые финальный hybrid gather исключает. Она также использовала геометрический вес без radial visibility, редкую случайную генерацию и запрет новых образцов после 32 соседей. Запечённая плотность влияла на старение живых проб. В результате достаточного покрытия поверхности не было даже после ожидания: промежуточное исправление оставляло 491 пиксель без GI на верхней части шара и через 2,2 секунды.

**Рабочее изменение:** GI G-buffer теперь хранит принадлежность baked receiver в alpha нормали. В hybrid статические поверхности исключены из поиска живых проб и финального динамического gather. Проверка живого покрытия вызывает общий `resolveIrradiance` с теми же пространственными, направленными, временными и radial-depth весами. Pinned-пробы могут дать начальное освещение дочерней пробе, но не засчитываются как живое покрытие и не создают штраф за плотность в lifecycle. Настоящий пробел запрашивает новый образец; голосование ограничивает добавление одним образцом на tile 8×8. Молодым пробам дают завершить начальное накопление, чтобы не создавать дубликаты. Геометрическое удаление «лишних» проб в hybrid отключено: без проверки visibility оно не доказывает избыточность; старение и штраф за живую плотность остаются.

При непрерывном движении обнаружился отдельный первый чёрный кадр: новая проба уже прошла integration, но её fade равнялся нулю. В hybrid она теперь получает минимальный относительный вес 1/4; confidence и visibility продолжают действовать. Это использование рассчитанного образца, без добавления ambient-подсветки.

**Проверка результата:** `scripts/check-dynamic-coverage.mjs` читает coverage alpha только на незапечённой геометрии; фон исключён через GI albedo G-buffer. Сценарий `legacy` воспроизвёл 6208/6208 пикселей без GI в стартовом кадре и 14/26645 в косом ракурсе. Исправленная проверка трёх фиксированных поз дала 0 пропусков; с `GI_CONTINUOUS=1` три кадра непрерывного движения также дали 0 пропусков на 5394, 4799 и 11802 пикселях шара. GPU-пиксели статической fallback-карты совпали побитно во всех случаях. Ошибок браузера нет. Свежие кадры `shots/dynamic-coverage/fixed/` и `fixed-moving/` просмотрены лично.

`check-frozen-static.mjs` повторно подтвердил default hybrid, frozen static, 1 bake при принудительном холодном запуске, неизменную карту после движения камеры/шара и освещённую наружную стену при 0 резидентных детальных страницах. Кадр `shots/frozen-static/outside-fallback.png` просмотрен. `check-hybrid.mjs`: при выключении динамического GI 580516 внутренних пикселей статики не изменились, 6196 пикселей незапечённого шара изменились; движение и resize прошли без ошибок. Typecheck, production build и diff check прошли.

**Граница итерации:** отсутствие coverage holes не означает идеальное освещение. В кадре непрерывного движения `fixed-moving/oblique.png` видна пятнистость GI на шаре. Следующий полезный шаг — устранить её через согласованное освещение и повторное использование данных на движущейся поверхности. Общая grid всё ещё содержит плотный pinned atlas, сканирование ограничено 512 элементами, отдельного компактного поля света для динамики пока нет. Ни качество на всех траекториях, ни масштабируемость всего мира этой проверкой не доказаны. Полный goal остаётся активным.

## Итерация 06 — пробы следуют за движущейся поверхностью

**Причина крупных пятен:** живые пробы оставались на прежних мировых координатах после перемещения шара. Они могли оказаться внутри него и накопить тёмное освещение, а новые участки постоянно требовали новых проб. Нулевое число coverage holes не обнаруживает этот дефект.

**Изменение:** `surfelMotion.ts` сохраняет локальную позицию, нормаль, владельца и birth stamp новой пробы. Перед integration GPU переносит их текущей матрицей меша; обратная транспонированная матрица переносит нормаль. Поиск покрытия и lifecycle обращаются к предыдущей grid по предыдущей позиции приёмника. Gather не смешивает пробы разных зарегистрированных движущихся мешей. Старые radial-depth данные очищаются после перемещения; плавное движение сохраняет историю irradiance, большой скачок/поворот сбрасывает её и guiding. Сброшенная история получает тот же warmup интегратора, что новая проба. Статические pinned-пробы не изменяются.

**Проверка:** `node scripts/check-rigid-surfels.mjs` проходит одну траекторию с переносом и поворотом; `$env:RIGID_SURFELS='0'` включает прежнее мировое размещение. Проверка читает реальные GPU-позиции и anchors, требует сохранения тех же локальных координат у сохранившихся проб и проверяет попадание в геометрию тестового шара. В зафиксированном проходе сохранились и переместились 74 исходные пробы; максимальная ошибка переноса меньше 0,000001 м. Отклонение от идеальной сферы меньше 0,003 м и соответствует её треугольной сетке. В старом варианте пробы оставались до 2,60 м от актуальной поверхности. Конец прохода: 78 живых проб с привязкой против 300 без неё. Это число проб конкретного сценария, не оценка FPS. GPU-пиксели статической fallback-карты совпали побитно. Свежие headed-кадры в `shots/rigid-surfels/attached/` и `world/` просмотрены на одинаковых позах: крупные тёмные пятна заметно уменьшились.

## Итерация 07 — динамика читает общие запечённые страницы

**Коррекция направления:** пользователь справедливо указал, что уменьшение буфера привязок не решает основной перерасход. Предыдущий runtime сохранял одну полноценную texel-пробу на каждый образец atlas: 180850 pinned-проб и pool на 262144 слота даже для одного шара. Теперь плотный pool нужен только во время authoring bake.

**Работающий путь по умолчанию:** static BVH сохраняет lightmap UV каждого вершины в отдельной RG32F-текстуре. Существующий интегратор Webgiya при попадании в запечённую статику интерполирует UV по barycentric coordinates и читает те же виртуальные страницы, которыми освещается raster. Проверка видимости остаётся в существующем static/dynamic BVH. Direct bounce и emission сохраняют прежних владельцев; прочитанный indirect умножается на albedo попадания ровно один раз. Нового path-tracing алгоритма не добавлено.

Compute-сэмплер задаёт слой DataArrayTexture и mip явно через WGSL, обходит проблему r182 с потерей слоя у TSL explicit-LOD array sample. Он использует тот же parent fallback и fade, что raster. При отсутствии страницы остаётся постоянно резидентная грубая карта. Исходные diffuse UV/material id не заменены lightmap UV. Sentinel -1 обозначает геометрию без развёртки; dynamic/unbaked hits сохраняют существующий cache lookup.

**Память и загрузка:** после сохранения authoring-данных GPU-буферы большого pool явно уничтожаются через backend Three r182; уничтожаются и прежние выделения при росте pool. Runtime создаёт общий pool на 4096 живых проб независимо от плотности atlas. Вместо прежних примерно 195 MiB на surfel pool теперь выделяется 3194940 байт, около 3,05 MiB, включая anchors и малые allocator buffers. В Cornell дополнительно 2304 байта занимает таблица BVH lightmap UV, 1385984 байта — виртуальные lightmap-текстуры. Это не вся память рендера: BVH, grid, материалы и framebuffer сюда не входят. При восстановлении manifest четыре массива authoring surfels вообще не запрашиваются и не распаковываются. Форматы authoring-файла и manifest сохранены; большие массивы пока остаются на диске для прежнего пути и повторного authoring.

`?bakedHits=0` оставляет прежний runtime с pinned parents для сравнения. Anchors теперь имеют явный диапазон и нулевой sentinel вместо обязательного массива на всю плотность atlas; все потребители пересобирают bindings при смене этого буфера. В default runtime anchors занимают 131104 байта, преобразования объектов учитываются отдельно. Пул общий, его расход не умножается на количество шаров.

**Проверка настоящего использования:** `node scripts/check-baked-transport.mjs` запускает 1 шар, затем 11 шаров в новом процессе Chrome. Второй процесс использовал тот же ключ и побитно ту же fallback-карту, bakeRuns=0, не запросил ни одного parent chunk. Все 11 владельцев присутствовали в живых пробах. На 15428 пикселях динамики с детальными страницами и с нулём страниц, затем на 15365 пикселях после движения: 0 coverage holes, все проверенные пиксели имели ненулевой GI. Живых проб соответственно 327, 322 и 302; ёмкость везде 4096. Ошибок WebGPU нет. Headed-кадры `shots/baked-transport/11-pages.png` и `11-moved.png` лично просмотрены. Это проверка совместного освещения и памяти, не заявление о FPS или окончательном качестве.

`check-dynamic-coverage.mjs` прошёл три прежних ракурса с 0 holes. `check-rigid-surfels.mjs` сохранил 74 исходные пробы после движения, ошибка переноса меньше 0,000001 м, статическая карта неизменна. Новый cold/save/load путь в `check-bake-persistence.mjs` дал одинаковые fallback-пиксели и 580516 внутренних beauty-пикселей статики без отличий.

**Открытые границы:** это устранение зависимости runtime-памяти от числа bake texels. Динамические лучи и рефит dynamic BVH всё ещё стоят работы, и больше движущихся поверхностей требует больше живых проб. Фиксированный pool имеет конечный бюджет. Выборка запечённого света пока использует virtual mip 1; footprint и запросы страниц от GI-лучей ещё не реализованы. Произвольный spawn/despawn, skinned/deformed receivers, signed indirect-коррекция на статике, качество переходов и дальнейшее удешевление динамики остаются задачами. `?movers=11` — тестовая сцена с объектами, добавленными до buildScene, не runtime spawn API. Полный goal не завершён.

Итоговые проверки итерации 07: полный `check-bake-persistence.mjs` прошёл cold/save/load, изменение солнца и восстановление после повреждённого chunk; ошибок браузера нет. `check-frozen-static.mjs` подтвердил default hybrid/staticFrozen=true, единственный принудительный bake, неизменные пиксели карты и освещённую наружную стену с нулём детальных страниц. Свежие `outside-fallback.png` и `rigid-surfels/attached/pose-0.4.png` просмотрены лично. Typecheck и production build (423 modules) прошли; diff check с корректным учётом CRLF прошёл. Начальный прогон сравнения 1/11 был прерван изменением исходников другой задачи между процессами: консервативный source hash закономерно потребовал другой bake. Повторный согласованный прогон использовал один ключ и прошёл без ослабления проверки карты. Сложные новые сценарии и оставшиеся пункты goal этим не закрыты.

## Итерация 08 — страницы запрашивает и сам GI

**Устранённая зависимость:** раньше резидентность определялась только камерой. GI-луч мог попасть в поверхность, подробная карта которой не попадала в выбранные камерой страницы, и бесконечно читать fallback. Теперь реальные static hits существующего интегратора формируют отдельные запросы в тот же кеш.

**Обратная связь:** в baked transport один из уже рассчитанных статических hits каждой живой пробы записывает lightmap UV, вес и frame stamp в неиспользовавшуюся runtime-диагностику `SurfelMoments.hit`. Новых лучей и storage bindings в интеграторе нет. Отдельный короткий compute извлекает только записи актуального кадра: 4096 vec4, 65536 байт. CPU получает не весь double-buffered irradiance cache, а этот небольшой массив. Одновременно выполняется не больше одного асинхронного readback, запуск не чаще 150 ms. Это дополнительный GPU-буфер 64 KiB и временный readback; память физических lightmap-страниц и live pool не увеличены. Смена bake/pool инвалидирует старые результаты через epoch и освобождает буфер.

**Общий бюджет:** запросы камеры и GI объединяются до загрузки. Для GI-страниц, не прошедших исходный отбор камеры, доступна четверть физических слотов (минимум один) либо свободное место камеры. Общие страницы сохраняются предпочтительно. Небольшое преимущество уже резидентной страницы, сглаживание голосов и срок 750 ms уменьшают колебания стохастических запросов. Сохраняются общий максимум страниц, 4 HTTP-запроса одновременно, 2 upload за кадр, checksum/cancellation/retry и parent fallback. Это рабочая политика распределения, не доказанный оптимум для любых сцен.

**Проверка:** `node scripts/check-gi-page-feedback.mjs` показал реальный запрос `1/1/1`, отсутствовавший в исходном отборе камеры. При общем бюджете 8 страниц он был принят без роста кеша. Затем тест выключил оба производителя запросов и очистил residency: осталось 0 страниц, динамика продолжила получать свет из fallback. После включения только GI реальные попадания самостоятельно загрузили 3 страницы; ручных запросов тест не добавляет. Запечённые GPU-пиксели оставались побитно теми же. В кадрах на 6208 пикселях шара, затем на 12858 после движения и смены камеры — 0 coverage holes, ненулевой GI во всей проверенной маске. Ошибок браузера нет. Кадры `shots/gi-page-feedback/both.png` и `gi-only.png` просмотрены лично.

Проверка с `$env:GI_FEEDBACK_SLOTS='2'; node scripts/check-gi-page-feedback.mjs --rebake` прошла те же сценарии при двух физических страницах, затем настоящий `re-bake now` через существующую кнопку. Новые записи обратной связи появились после замены bake/pool, старые не загрязнили новое состояние, ошибок readback/WebGPU нет. Явный rebake допускает новые накопленные значения, поэтому побитная неизменность проверяется только до него.

**Согласование общего checkout:** параллельная правка временно изменила `giShadeHit` с 11 на 12 аргументов, что обнаружилось как настоящая ошибка WGSL в проверке двух страниц. ## Итерация 09 — выбор детализации lightmap по footprint попадания

**Изменение:** динамический GI больше не читает постоянный mip 1. `bakedHitLod.ts` переводит диаметр конуса луча в atlas texels через мировые вершины и UV конкретного hit-треугольника, учитывая растяжение chart и угол попадания. Максимальная ось проекции определяет дробный LOD для существующего trilinear sampler. Вырожденные треугольники и скользящие углы ограничены конечным fallback. Используются уже привязанные BVH positions и UV; новых лучей, storage bindings и буферов не добавлено.

Диаметр начинается с размера пикселя выходного framebuffer: проекция камеры, реальное разрешение с DPR и длина camera→receiver→hit. Для ортографической проекции ширина постоянная. Это локальная гипотеза распространения конуса через плоское отражение, без производных BRDF/кривизны. Радиус поиска соседних surfels не принимается за ширину фильтра: это неоправданно размыло бы карту. Первоисточник принципа и границы адаптации указаны в `render-research-2026-09-07.md`; физическая точность и оптимальность этой ширины не объявляются доказанными.

**Связь со streaming:** выбранный floor(LOD) упакован вместе с importance в прежнюю запись обратной связи. Readback остаётся 64 KiB, общий pool — 3194940 байт, кеш страниц — прежнего размера. Запросы начинаются с реально используемого mip, включают coarser parents и не требуют более мелких страниц. При LOD постоянного fallback запросы сходят к нулю после обычного срока устаревания. Compute sampler пропускает физические texture samples уровней с нулевым весом. Близкие попадания теперь могут требовать mip 0, поэтому это не обещание снижения всего трафика относительно прежнего фиксированного mip 1.

**Проверено на настоящем GPU:** `node scripts/check-baked-lod-math.mjs` исполняет production WGSL для девяти аналитических случаев: один/два texels, дробный mip 0.5, масштаб мира, растяжение и поворот UV, угол 60°, вырожденный треугольник, fallback clamp. Ошибка относительно ожидаемого LOD меньше 0.00001. Это проверка проекции/математики, не дубль функции на CPU.

`node scripts/check-gi-page-feedback.mjs --lod` прошёл при 8 страницах. При принудительном LOD 0 реальные hits запрашивали mip 0 и родителей; при LOD 1 остались только четыре страницы mip 1; при LOD 2 — 0 страниц/запросов. ## Итерация 10 — изоляция UV charts в lightmap mip-цепочке

**Найденные дефекты:** прямоугольники charts не были выровнены по downsample-блокам, а полутексельный inset защищал только mip 0. Грубые уровни смешивали соседние поверхности. Глобальное GPU gutter fill не знало владельцев texels; последующий `dilateUnlitTexels` также мог брать свет из другого chart и заменял измеренные тёмные texels по порогу яркости.

**Изменение:** `assignLightmapUvs` возвращает прямоугольники отдельных charts и `safeMip`. Размеры и координаты упаковки кратны `2^safeMip`, UV inset удерживает bilinear footprint внутри первого/последнего texel этого mip. Минимальный базовый отступ также разделяет соседние charts для существующего 3×3 denoiser. Для обычного 512² atlas/fallback 128² это выравнивание по 4 texels и inset 2 texels. Padding занимает место внутри прямоугольников; дополнительный межпрямоугольный gap не нужен. Плотность по-прежнему определяется упаковщиком для всей сцены, размер atlas не увеличен.

`lightmapSurfels` сохраняет alpha измеренных образцов при финальном blit. Проверка не перекрашивает тени по яркости. Это исправление границ данных, не решение bake-позиций внутри пересекающейся геометрии.

## Итерация 11 — добавление и удаление динамических объектов во время работы

Добавлен `SurfelGI.syncDynamicScene(renderer, scene, { materialsChanged? })`: один вызов после пакета изменений сцены. Он заменяет только динамический BVH и зависимые compute bindings. Статический BVH, его геометрия и UV, запечённые страницы и общий пул остаются на месте. Обычное движение продолжает вызывать прежний `updateDynamicScene()`, без регистрации всей сцены на каждом кадре.

При изменении набора материалов пересобирается общая diffuse/emission array. Статические triangle material IDs переводятся в новые номера только при необходимости; их геометрия не перестраивается. Перевод опирается на статических владельцев: динамический материал, прежде деливший с ними deduplicated layer, не должен менять материал статических треугольников при смене своего цвета. Удалённые материалы больше не удерживают слои после синхронизации. Старые material render targets, временные bake-материалы и динамические GPU buffers освобождаются.

Выявлена ошибка перенумерации владельцев: после удаления соседей неподвижные raster meshes могли сохранять старый owner uniform. Непосредственный GPU readback показывал правильный remap существующих anchors, но вновь рождённые получали старые IDs 7/9/11 вне уменьшенной таблицы, попадали в нулевые координаты и заполняли весь пул. Теперь surviving receivers сохраняют свои слоты, а свободные номера повторно используются. Таблица содержит четыре mat4 на слот и допускает промежутки; её верхняя граница не растёт с количеством циклов удаления/создания. Удаление освобождает только пробы удалённых мешей; замена геометрии инвалидирует её прежние anchors. История света остальных сохраняется.

После смены состава сцены сбрасываются радиальные данные видимости живых surviving probes: даже неподвижный приёмник больше не должен доверять прежнему набору препятствий. На одном промежуточном прогоне после repack материалов возникло 1369 незаполненных пикселей на грани куба без ошибочных owner IDs. В следующем прогоне это не повторилось ещё до изменения visibility, поэтому единственная причина этого переходного дефекта не доказана. Очистка устаревшей видимости исправляет отдельную некорректность состояния; финальный прогон также прошёл без провала. Мгновенная сходимость на каждом промежуточном кадре не заявляется.

`node scripts/check-runtime-movers.mjs` проверил в одном headed Chrome: исходный шар → добавить десять новых объектов/материалов → удалить пять → занять освободившийся слот → переместить оставшихся → удалить всех → создать три новых. Во всех семи снимках capacity=4096, static BVH identity прежняя, fallback pixels побитно неизменны, дополнительных bake нет, ошибок WebGPU/браузера нет. При 11 объектах живых проб было 297; после удаления пяти — 174; после полного удаления — 0. Число material UUIDs изменилось 4→14→9→10→3→6. Повторно занят первый свободный receiver slot 2, номера соседей и часть исходных sid/birth сохранены. Максимальная ошибка переноса anchors меньше 0.000001 единицы мира.

В финальном прогоне на 21385 пикселях добавленной динамики, 14458 после удаления, 15831 после повторного использования слота, 16093 после движения и 4174 после нового создания — 0 coverage holes и ненулевой GI во всей маске. Свежие `shots/runtime-movers/added-ten.png`, `moved.png` и `respawned.png` просмотрены лично. `check.json` и snapshots anchors содержат фактические владельцы и данные проверки. Это функциональная проверка изменения сцены, не FPS-бенчмарк.

Открыто: предел 1024 rigid receiver slots, skinned/instanced/deformed anchors, повторная вставка того же ранее удалённого Mesh при изменившемся ID и observer caching, общий merged dynamic BVH вместо instance hierarchy, полная перепаковка material array при изменении membership. Сохранение baked pixels ещё не даёт signed indirect-коррекцию от динамики на статике. Полный goal остаётся активен.

## Итерация 12 — движение без перестройки треугольников

Прежний `dynamicBvh.refresh()` преобразовывал все вершины/нормали в мировые координаты, заново строил MeshBVH и загружал nodes/positions/normals/indices при движении любого объекта. `dynamicHierarchy.ts` заменяет эту часть immutable object-space BLASes и небольшим world-space TLAS. Меши с одним geometry/material template разделяют дерево геометрии. TLAS строится по центрам bounds при создании bundle; при обычном движении его топология сохраняется, bounds обновляются снизу вверх. `syncDynamicScene` по-прежнему заменяет bundle при изменении состава сцены.

В прежний attribute storage после UV/material records добавлены пять записей vec3 на instance: root/validity и четыре столбца affine inverse. Эти записи имеют явный stride 16 bytes. Это сохраняет прежние 14 storage bindings integrator и не требует texture fetch для матриц. При движении загружаются только изменённые записи и префикс TLAS в общем node buffer; BLAS nodes, позиции, индексы и UV не обновляются. Неиспользовавшийся dynamic normal buffer убран. Обратный луч не нормализуется, поэтому его параметр t остаётся мировым расстоянием при неравномерном масштабе и shear; нормаль преобразуется inverse transpose. TLAS bounds имеют небольшой консервативный отступ при округлении в float32. Вырожденный instance с нулевым determinant отключён для пересечений.

Проверка `node scripts/check-dynamic-hierarchy.mjs` запускает production traversal на GPU и сравнивает с Raycaster по исходным raster meshes. Три положения по 1734 луча: исходное, движение одного объекта, затем масштаб/shear/перемещение InstancedMesh instance. На сцене семь экземпляров и два local trees. Совпали hit/miss, расстояние, UV/material и нормаль; максимум ошибки расстояния 0.000001799, UV 0.000003183, нормали меньше 0.000000087. Никакого отдельного интегратора света или path tracer для проверки не добавлялось.

Перехват реальных `GPUQueue.writeBuffer` подтвердил: движение одного объекта отправило 416 bytes TLAS и 80 bytes instance record — всего 496 bytes. Изменение трёх отправило 656 bytes. Записей в position/index buffers нет, их версии остались нулевыми. В отсутствие движения refresh возвращает false. Это доказательство устранённой работы, не замер FPS и не утверждение об ускорении всего GPU-кадра: обход теперь содержит два уровня и две traversal stacks.

При проверке обнаружена особенность Three r182: upload adapter перепаковывает storage vec3 в четыре слова и меняет CPU array. В динамическом attribute buffer stride теперь задан сразу, поэтому обновление матриц не перепаковывает весь массив. В `refreshSceneMaterials` также исправлен обход padded static records: раньше UV/padding могли читаться как IDs. GPU-проверка удаления материала перед статическим материалом сохранила UV всех 504 вершин и правильно перевела ID 1→0.

Полный `check-runtime-movers.mjs` прошёл создание 11 объектов, удаление пяти, повторное использование слота, движение семи, полное удаление и создание трёх. Bake и static BVH остались неизменными, дополнительных bake нет, pool capacity=4096, ошибок WebGPU нет. После движения hierarchy обновилась один раз, position/index versions остались нулевыми. В финальном прогоне на 21385/14458/15831/16093/4174 пикселях динамики coverage holes=0, GI ненулевой во всей маске.

В одном предыдущем прогоне после движения пропало покрытие всех 1829 пикселей owner 9; повторный прогон прошёл. Аналогичный дефект был до замены hierarchy в итерации 11. Точная причина не установлена; его нельзя считать исправленным благодаря одному прошедшему прогону. GPU-проверка пересечений не заменяет проверку lifecycle/coverage. Это следующая конкретная ошибка для разбора, наряду с прежней проблемой повторной вставки того же Mesh.

Начальный `shots/dynamic-hierarchy/before.png`, промежуточный `shots/runtime-movers/moved.png` и финальный `shots/dynamic-hierarchy/after.png` лично просмотрены. Финальный кадр снят после окончания bake с 11 объектами в изменённой позе; первое изображение, снятое до окончания загрузки, заменено. Typecheck, production build (426 modules) и scoped diff check прошли. Сохраняются предупреждение сборки о размере chunk и прежнее предупреждение Inspector во время authoring bake.

Открыто: перепостроение bundle при spawn/despawn, разделение одинаковой геометрии с разными material templates, качество TLAS после больших перемещений, деформации и dynamic indirect-коррекция статики. Полный goal остаётся активен.

## Итерация 13 — убрать пустую работу привязки проб

В `surfelMotion.prepare` раньше каждый кадр вычислялись inverse/normal matrices всех rigid receivers, загружалась целиком таблица четырёх mat4 на каждый slot и запускался проход переноса anchors, даже когда объекты неподвижны. Теперь полная запись обновляется только при инициализации или изменении matrixWorld. На первом кадре после остановки отдельно обновляется предыдущая матрица: она должна соответствовать положению, в котором построена сетка предыдущего кадра. Дальнейшие неподвижные кадры не загружают таблицу и не запускают перенос. Активация и замена pool/anchors сохраняют обязательный начальный проход. Обычный расчёт освещения остаётся live; неподвижность приёмника не означает неизменность света.

`node scripts/check-rigid-motion-work.mjs` проверяет production transport на GPU для 11 receivers. Перехват реальных `queue.writeBuffer` подтвердил: движение одного — 256 bytes только его записи; остановка — один раз 64 bytes previous matrix; следующие неподвижные кадры — 0 bytes и 0 запусков Move Rigid Surfel Anchors. Проверены повторное начало и непрерывное движение, текущая/предыдущая позиция, положение и нормаль anchors. Максимальная ошибка позиции меньше 0.000000364, нормали меньше 0.000000006. Это данные только таблицы привязки, не стоимость всех GI-проходов. Первичная GPU allocation не включена в сравнение последующих кадров.

Проверка поймала особенность Three r182: updateRanges, поставленные до первой GPU allocation, не очищаются при создании буфера. Они заставляли первую подвижку повторно отправлять все 11 записей. Теперь диапазоны добавляются только для уже загруженного GPU buffer; первая allocation получает полный актуальный CPU array.

`check-rigid-surfels.mjs` прошёл три положения анимированного шара, сохранив локальные координаты surviving anchors и побитно неизменный bake. Полный `check-runtime-movers.mjs` с `GI_STEPS=200 GI_DEBUG=1 GI_SETTLE_FRAMES=600` прошёл добавление десяти объектов, удаление пяти, повторное использование слота, движение, выдержку дольше TTL, полное удаление и создание трёх новых. В этом прогоне 297 live samples обслуживали 11 объектов из общего pool capacity=4096. После движения и выдержки: 135 live samples, 16093 пикселя динамики, coverage holes=0. Static BVH, bake и позиции/индексы BLAS не менялись. Это функциональная регрессия, не доказательство устойчивости во всех состояниях или повышения FPS.

До изменения транспорта повторно воспроизведён старый дефект покрытия: owner 7 потерял все пробы, 1442 его пикселя остались без GI. В пуле было 128 живых проб, свободная очередь корректна, но spawn flags отсутствовали. Причина не установлена; последующие успешные прогоны, в том числе ещё до оптимизации, не исправляют этот факт. Для следующего разбора добавлен включаемый только по запросу GPU-снимок решения FindMissing на конкретном незаполненном пикселе и управляемое продвижение GI-кадров. Диагностика не выделяет debug buffer по умолчанию и не добавляет runtime readback; файлы новых неудачных прогонов складываются в отдельные каталоги, чтобы следующий успешный прогон не подменил их anchors.

Свежие кадры до изменения, промежуточный `shots/rigid-surfels/attached/pose-1.2.png` и финальный `shots/runtime-movers/settled.png` просмотрены лично. Typecheck, production build (426 modules) и scoped diff check прошли. Прежнее предупреждение о размере chunk остаётся. Интермиттирующая потеря покрытия, ограничение rigid receivers, стоимость остальных GI-проходов и dynamic indirect-коррекция на статике остаются открытыми; полный goal не завершён.

## Итерация 14 — актуальный владелец GI при повторном добавлении меша

Воспроизведён отдельный дефект owner uniform: три неподвижных меша с общим материалом выводили владельцев -1/-2/-3. После изменения GI slot среднего меша на 7 GPU продолжал выводить -2. Переключения этого меша в baked и unbound также не меняли значение. Причина — NodeMaterialObserver Three r182 сравнивает свойства материала/геометрии/матрицы, но не внешний MRT uniform, получающий значение из userData. Это ошибка назначения проб, а не нехватка плотности.

receiverOwnership.ts дополняет штатный observer сравнением baked/rigid owner для каждого RenderObject. Исходные проверки и bookkeeping вызываются по-прежнему. При смене владельца uniforms обновляются; без смены дополнительного принудительного refresh нет. Подготовка выполняется один раз для материала при buildScene/syncDynamicScene. Cache-key suffix устанавливает новый observer и для ранее скомпилированных материалов. Изменение owner после подготовки не меняет material version или shader key. Поддержаны shared materials, сохранены существующие setupObserver/customProgramCacheKey через вызов исходных методов.

`node scripts/check-receiver-owner.mjs`: before.json фиксирует старые -2 после всех переключений; check.json после исправления содержит последовательность -2 → -7 → 1 → 0 → -2 для среднего меша, соседи неизменны. Fixture устанавливает observer после первого GPU render, повторяет подготовку и проверяет отсутствие повторного wrapping/перекомпиляции при смене владельца. Ошибок WebGPU нет.

Для проверки восстановления покрытия добавлена audit-only команда expireReceiver: она записывает kill signal выбранным пробам, после чего их удаляет штатная economy, а FindMissing/Allocate восстанавливают покрытие. Этот сценарий прошёл ещё до исправления observer: прежние sid/birth исчезли, через восемь кадров видимый приёмник снова полностью покрыт. Поэтому неисправность allocator/free-list не подтверждена. На случай новой редкой потери покрытия on-demand snapshot теперь сохраняет и фактический WGSL FindMissing; регулярных чтений GPU не добавлено.

Полный headed прогон check-runtime-movers.mjs с GI_STEPS=200, GI_SETTLE_FRAMES=600, GI_EXPIRE_OWNER=7, GI_REINSERT=1 и выключенным GI_DEBUG прошёл. После spawn/remove/reuse/move и выдержки проверено удаление того же Mesh из сцены без dispose, занятие его прежнего slot 3 другим объектом и возвращение прежнего Mesh в slot 4. UUID проверен: это тот же объект и материал в прежней позе. В возвращённой сцене 8 движущихся объектов, 152 live probes из общих 4096, 16855 пикселей динамики, coverage holes=0; новый slot 4 занимает 1566 пикселей. После удаления всех pool пуст; создание трёх новых также проходит. Bake побитно неизменен, static BVH прежний, дополнительных bake нет, triangle position/index versions не менялись. Ошибок браузера/WebGPU нет.

Свежий кадр перед исправлением, промежуточный settled.png и итоговый reinserted.png лично просмотрены. Typecheck и production build (427 modules) прошли, прежнее предупреждение chunk size остаётся. Исправление закрывает устаревший owner при смене GI-роли и повторном добавлении меша. Причинная связь с прежним редким исчезновением owner 7/9 не доказана; тот дефект не объявлен закрытым. Основной goal остаётся активным: качество динамического света, его бюджет, signed indirect-коррекция статики и остальные требуемые возможности ещё не доведены.

## Итерация 15 — детали virtual lightmap под скользящим углом

Прежняя изотропная выборка выбирала mip по длинной стороне footprint и размывала детали поперёк неё. Теперь raster sampler строит главные оси UV Jacobian, выбирает mip по короткой стороне с ограничением anisotropy=8 и усредняет от одной до восьми выборок вдоль длинной стороны. Это собственное линейное приближение, не полный EWA. Все выборки используют существующий WGSL resolver физических страниц, parent fallback и fade; GI hit-cone sampler остаётся изотропным.

Каждая выборка ограничена безопасными texel centres своего chart через новый lightmapBounds (16 bytes на вершину). Раскладка, UV, padding и формат сохранённого bake не менялись. CPU page demand хранит три UV треугольника и вычисляет перспективно-корректные производные в его экранном центре с тем же ограничением анизотропии. Это приближение запроса страниц, а не точный feedback каждого пикселя. Число физических страниц и ограничения загрузки прежние; объём текстур не вырос, но появились данные границ и дополнительные выборки, поэтому нулевой общей стоимости не заявляем.

`node scripts/check-anisotropic-lightmap.mjs` прошёл production GPU sampler на 544 точках каждого состояния: fallback, resident и eviction. На resident контрольном узоре ошибка сохранения поперечных полос снизилась с 0.318198 до 0.000214; остаток усредняемой частоты вдоль длинной стороны 0.003433. Подмешивание цвета соседнего chart и non-finite значения отсутствуют. Проверены граница физической страницы, поворот экранных производных, вырожденный footprint и совпадение CPU demand с выбранными mip. Texture allocation до/после: 822464 bytes. При отсутствии страниц фильтр закономерно использует грубый fallback и не восстанавливает отсутствующие детали.

`check-chart-filter.mjs` прошёл: для safeMip=2 по 810 точек fallback/resident без утечек; измеренные чёрные texels сохранены. `check-frozen-static.mjs` прошёл в основной сцене: startup bake один, камера и движение объектов не меняют bake, страницы вытесняются и возвращаются при неизменном texture allocation 1385984 bytes. Static frozen включён, динамический GI остаётся live. Ошибок WebGPU нет. Лично просмотрены оба изображения наклонной плоскости anisotropy 1/8 и кадры основной сцены с fallback/resident: детали вдали сохраняются лучше, прежнего чёрного провала на внешней красной стене нет. Typecheck и production build (428 modules) прошли; предупреждение о размере bundle прежнее.

Это локальное улучшение фильтрации, не benchmark FPS и не доказательство физической точности всего рендера. Предел coarsest mip, дискретные переходы числа выборок и большие перспективные треугольники требуют дальнейшей адресной работы при видимом дефекте. Редкая потеря live coverage и полноценная indirect-коррекция статики динамическими объектами остаются открытыми. Goal не завершён.

## Итерация 16 — общий бюджет обновления динамического GI

Раньше каждая живая проба независимо запрашивала base rays, ещё 12 при нестабильности или 32 во время прогрева. Общего лимита не было. `integrationSchedule.ts` выполняет GPU histogram, prefix и admission по 64 уровням приоритета. Новая история, изменение позиции/нормали и inconsistency повышают приоритет; время ожидания также повышает его. Порядок слотов вращается внутри одинакового приоритета. Стабильные приёмники проверяются каждые четыре GI update, чтобы изменение чужой тени или света не оставалось незамеченным навсегда. Это эвристика очереди, не доказательство универсального предела задержки при перегрузке.

По умолчанию hybrid допускает суммарно 4096 первичных GI samples за кадр; значение регулируется в GUI. Ноль доступен в audit как прежний неограниченный контроль. Статический bake не использует очередь. Отложенная проба копирует все пять vec4 истории read→write и не запускает лучи. Admission временно передаётся через hit.w выходного moments buffer, который интегратор затем полностью публикует. Это сохраняет прежние 14 storage bindings; первоначальная дополнительная binding не подходила лимиту устройства. Цена очереди — четыре коротких GPU-прохода и 48 bytes/slot + 768 bytes, для 4096 slots это 197376 bytes. Primary-ray limit не ограничивает стоимость BVH traversal в миллисекундах и не включает дополнительные shadow/depth rays.

`check-integration-schedule.mjs` проверил реальный GPU: 128 новых проб получили ровно 4096 samples; стабильные пропустили три update и получили 512 на четвёртом; перемещённая и сброшенная проба получили соответственно 4 и 32 при бюджете 36. В 160 перегруженных кадрах с бюджетом 64 превышений нет, на последнем шаге наибольшее ожидание 32 update. Проверены pinned/dead и повторное использование generation.

`check-runtime-ray-budget.mjs` проверил основной интегратор с 11 объектами. За 36 шагов запросы доходили до 8480, выдано ровно 256 на каждом шаге. Подтверждено 5254 побитно сохранённых полных историй при пропуске и 456 фактических обновлений накопления выбранных проб. После возврата к 4096: 21385 видимых пикселей динамики, holes=0, все освещены; bake побитно прежний, static BVH прежний, повторного bake нет. Ошибок WebGPU не зарегистрировано. Лично просмотрены unrestricted, промежуточный 256 и финальный 4096 кадры. Проверка также исправила audit.stepGI: одного renderer.info.frame недостаточно для PassNode, теперь продвигается NodeFrame.frameId; прежний одиночный вызов мог сохранять beauty первого шага.

Полный runtime-mover прогон после удаления пяти объектов вновь обнаружил известный дефект coverage у owner 7: 1440 пикселей без покрытия при 123 живых пробах и нулевых spawn flags. Контроль GI_RAY_BUDGET=0 прошёл spawn/remove/reuse/move/empty/respawn. Повторный прогон с admission и GI_DEBUG_LATE=1 дошёл до reuse и потерял 1369 пикселей owner 9. После включения диагностики только на уже обнаруженном пикселе и одного ручного шага FindMissing выдал resolvedWeight=0, pendingWeight=0, liveCount=2, wantSpawn=1; появились 36 spawn tiles. Это сужает следующий разбор до расхождения решения покрытия до/после смены compute graph или продвижения кадра. Эти два воздействия пока не разделены. Причина не доказана, влияние admission на частоту дефекта не исключено. Успешный узкий budget-check не заменяет этот провал полной регрессии.

Typecheck и окончательная production build (429 modules, 2m58s) прошли; прежнее предупреждение chunk size остаётся. Бюджет реализован и проверен, но временная устойчивость динамического GI остаётся незавершённой. Полный goal активен. Снимки неудач сохранены отдельно; контрольный успешный прогон не подменяет их доказательства.

## Итерация 17 — соседние объекты больше не вытесняют нужные пробы

Разделены повторный запуск FindMissing, обновление его uniforms и пересоздание compute graph. В неудачной сцене с 1369 отсутствующими пикселями owner 9 повтор исходного графа с прежними frame=666 и readOffset=0 изменил spawn flags с 30 до 36. Пересоздание не требовалось. Проверка сохранённого состояния показала: в этом же кадре восстановилась передняя грань owner 7, а у owner 9 остались только две пробы других граней. Это было чередование удаления и восстановления, а не необходимость пересобирать шейдер или увеличивать число лучей.

Причина — стоимость плотности в Surfel Economy. Она считала все live samples в ячейке, хотя пробы другого rigid receiver не могут освещать этот объект. При высокой суммарной плотности нелинейная стоимость могла удалить нужную поверхность после того, как FindMissing уже признал её покрытой. Из-за этого следующий кадр снова создавал пробы, а соседняя поверхность могла исчезнуть.

Hybrid count теперь включает только unpinned пробы с тем же действительным receiver owner и совместимой нормалью (dot > 0.8). Противоположные поверхности также не заменяют друг друга. Членство берётся из сетки до economy; проверка age < TTL внутри подсчёта намеренно отсутствует, иначе результат зависел бы от параллельного удаления соседей в том же dispatch. Это локальная эвристика избыточности, не универсальная модель достаточной плотности для любой геометрии. Новых буферов, проходов и лучей в runtime не добавлено; общий pool=4096 и ray budget=4096 прежние. Сохраняются полезные пробы, поэтому число живых samples может стать больше прежнего ошибочно сокращённого числа.

`check-receiver-economy.mjs` воспроизвёл ошибку на production GPU economy/grid/anchors: 128 разных receivers в одной ячейке с age=490 и keepalive=5 все удалялись за один шаг. После изменения все 128 живы, age остаётся 490. Контроль из 128 дубликатов одной поверхности по-прежнему удаляется. Две противоположные группы по 64 samples одного receiver сохраняются. before.json и check.json содержат реальные результаты GPU, ошибок WebGPU нет.

Обычный `check-runtime-movers.mjs` прошёл spawn/remove/reuse/move/empty/respawn. Расширенный прогон с GI_STEPS=200, GI_SETTLE_FRAMES=600, GI_REINSERT=1, GI_EXPIRE_OWNER=7 прошёл без включённых GI_DEBUG/GI_RECHECK: принудительно удалённые samples восстановились за восемь шагов; после выдержки больше TTL все 16093 пикселя динамики покрыты. Возвращён тот же Mesh с новым owner 4: 8 объектов, 479 живых проб из 4096, 16855 пикселей, holes=0. После полного удаления pool пуст; повторное создание трёх объектов также прошло. Bake побитно прежний, static BVH прежний, triangle position/index versions не менялись, браузерных ошибок нет.

Лично просмотрены исходная чёрная грань, исправленный removed-five.png и итоговый reinserted.png. Отдельная проверка упаковки нормалей не воспроизвела ошибку, поэтому формат не менялся. Audit-only replay/recheck оставлены для раздельной проверки inputs и graph, без дополнительной работы в обычном кадре.

Повторный `check-runtime-ray-budget.mjs` прошёл с новой economy: 36 кадров ровно по 256 admitted rays при запросах до 14536; 5328 полных историй сохранены при пропуске, 288 накоплений реально обновлены. После возврата к 4096 все 21385 пикселей динамики покрыты и освещены. Использован сохранённый bake, bakeRuns=0, pixels и static BVH неизменны, ошибок браузера нет. Typecheck, production build (429 modules, 2m49s) и scoped diff check прошли. Осталось прежнее предупреждение размера bundle. Эта итерация закрывает воспроизведённое взаимное вытеснение проб разных приёмников; она не доказывает качество всех будущих сцен или всех временных переходов. Полный renderer goal остаётся активным.

## Итерация 19 — зависимые от камеры полосы самозатенения

Пользователь прислал мелкие полосы внутри освещённой стены и на шаре. check-shadow-receivers.mjs воспроизвёл их; выключение только sun.shadow.intensity убирало полосы при сохранённом GI. Встроенный PCFSoftShadowFilter сравнивал соседние shadow texels с общей глубиной. На наклонной поверхности это ложное самозатенение, чей рисунок меняется при перепроецировании камеры.

Добавлен receiverPlaneShadow.ts, включён для обычного directional sun через main.ts. Производные shadow coordinates переводятся из экранных координат в градиент глубины по UV. Для каждого из 16 texels вычисляется своя глубина сравнения; separable weights дают непрерывно сдвигаемый фильтр 3x3. Используются raw textureLoad, чтобы аппаратный PCF не сравнивал ещё четыре разные точки с одной глубиной. У вырожденного Jacobian знаменатель ограничен с сохранением знака. ## Итерация 20 — кора и листья на пляже из биологии, а не из текстуры

Пользователь попросил физически точные материалы коры и листьев для сцены `?scene=beach`, построенные с нуля. Прежние материалы были ручными цветами: лист — `vertexColor` с view-зависимой «просвечивающей» эмиссией, ствол — тайлящаяся 256×256 картинка колец. Новая реализация выводит оптику из строения ткани.

Лист. `src/entities/foliage/leafOptics.ts` реализует пластинчатую модель PROSPECT (Jacquemoud & Baret 1990; Féret et al. 2008): N элементарных слоёв мезофилла с показателем преломления 1.44→1.40, Френель на границах усреднён по конусу падения (40° сверху, 90° внутри), пропускание слоя по Беру, проинтегрированное по полусфере через E1, решение Стокса для N−1 слоёв. Поглощение задают пигменты: хлорофилл a+b (сильно в синем и красном, минимум на 550 нм), каротиноиды (только синий), бурые пигменты мёртвой ткани. Спектры R и T на 400–700 нм интегрируются под D65 с наблюдателем CIE 1931 в линейный sRGB. Пресеты (`LEAF_PRESETS`) — зрелый и молодой листочек кокоса, стареющий, мёртвый, плотный широкий лист, веер — по диапазонам LOPEX/ANGERS. `scripts/leaf-optics-fixture.ts` проверяет: у листа без пигментов R+T=1, зелёный пик на 550 нм, R(550)=0.142, T(550)=0.173, синий и красный ниже 0.06, красный край, сохранение энергии у всех пресетов, молодой лист светлее, мёртвый — бурый. Первый прогон показал пик на 530 нм: минимум таблицы поглощения хлорофилла был сдвинут; исправлено.

BSDF. `leafMaterial.ts` — `MeshPhysicalNodeMaterial` с собственной `LightingModel`: ламбертово отражение R, пропускание T·p(θ)·E(−n), спекуляр кутикулы GGX с F0 из n=1.42. Пропускание считается внутри lighting model, поэтому карта теней солнца действует и на просвет: лист в тени другого листа не светится. Угловое распределение прошедшего света — не ламбертово: доля 0.35 идёт в лоб Хеньи–Гринстейна с g=0.55 вокруг продолжения солнечного луча (по измерениям BTDF листьев, Bousquet 2005), остальное диффузно. R и T лежат в вершинных атрибутах `color` и `transmittance` и меняются вдоль листа: кончик — более молодая ткань. Жилки без хлоропластов: маска жилок в B-канале карты шероховатости добавляет первую поправку ΔR/ΔT, посчитанную той же оптикой при 0.45 Cab. В контровом кадре сеть жилок просвечивает светлее пластинки, как в жизни.

Наклоны физические (метры). Адаксиальная сторона восковая (roughness 0.30), абаксиальная матовая (0.55), выбор по `frontFacing`. Одна карта на вид, общая для всех растений.

## Итерация 21 — воздух на пляже: froxel-туман и veiling glare

Пользователь спросил, за счёт чего в UE5 и Northlight появляется ощущение воздуха, и попросил применить это к `?scene=beach` одним проходом, с переключателем. Уточнение в ходе работы: цель — не туман как таковой, а то, что в жизни объекты «примешиваются» друг к другу и нет жёстких переходов между по-разному освещёнными поверхностями. Реализованы два переносящих свет между пикселями слоя, оба выключаемые.

Туман. `src/shared/render/atmosphere/volumetricFog.ts` — froxel-объём 160×90×64 (`Storage3DTexture`, rgba16float), экспоненциальные срезы по глубине между `near` и `far`. Проход scatter (compute, поток на froxel): позиция с джиттером Halton(2,3,5); плотность = базовая × exp-спад по высоте от `baseHeight` × мягкий box вокруг плиты × два октавы Perlin с ветром; солнце берётся из реального shadow map солнца (raw `textureLoad`, та же `shadow.matrix`, что у поверхностей, тот же знак сравнения, что в `receiverPlaneShadow.ts`), фаза Хеньи–Гринстейна с изотропной долей 0.15; небо — изотропный вклад средней radiance окружения (`meanEnvironmentRadiance`, Uint16 half-float декодируется, солнечные пиксели обрезаны 4× средней яркости, иначе солнце учлось бы дважды). Результат `(σ_s·L_in, σ_t)` смешивается с историей прошлого кадра, перепроецированной через предыдущую view-projection (0.9). Проход integrate (поток на столбец экрана): аналитическое интегрирование по срезам `S(1−e^{−σl})/σ`, в каждом срезе хранится накопленный in-scatter и transmittance. В composite (`FrameGraph.setAtmosphere`) после overlay-воды и до FXAA: `colour·T + L_in` по глубине пикселя; глубина — минимум сцены и overlay, поэтому вода туманится по своей поверхности, а преломление читает нетуманный цвет. Первый кадр без shadow map туман неактивен (`uActive`), чтобы не читать нулевой объём. Пресет пляжа: σ_t 0.03 1/м у уровня воды, спад 0.4 1/м, солнце ×4, небо ×1.0, g 0.65. `?fog=0|1`, `?fogDensity= fogSun= fogSky= fogNoise=`, `?fogView=inscatter|transmittance`; GUI «Atmosphere». Для Cornell по умолчанию выключен: пресет задаёт сцена (`SceneHost.atmosphere`).

Разделение при отладке: `fogView=inscatter` показал корректную окклюзию плитой (глубина и ориентация UV верны), `fogSky=0` — слабые, но реальные лучи через shadow map у камней и пальм, `fogSun=0` — гладкий голубой in-scatter, `fogView=transmittance` — мягкий box без бандинга. Числа: средняя radiance неба HDR после обрезки (0.151, 0.212, 0.317); ошибка `THREE.TSL: Invalid generated code, expected a "vec3"` (48 раз) воспроизводится и при `?fog=0`, отсутствует в Cornell — это параллельные правки материалов пляжа, не туман; проверка сравнивает множества ошибок on/off и требует отсутствия *новых*.

Veiling glare. `FrameGraph.setGlare` — `bloom` из three (mip-цепочка) с порогом 0 поверх HDR после тумана. Это не «свечение ярких объектов», а доля света каждого пикселя, рассеянная объективом/глазом на соседей: смягчает контраст на границах освещённой и затенённой поверхностей. Первая версия прибавляла bloom со strength 0.08, и пользователь верно отметил «слишком ярко»: пять mip-уровней BloomNode суммируются с весами, всегда дающими 3.0, то есть плоское поле возвращалось втрое ярче и прибавка 0.08 поднимала тени на ~0.24 освещённого соседа. Теперь spread делится на 3 (единичное усиление) и *смешивается* с кадром долей strength (0.04 по умолчанию) — энергия сохраняется: освещённый песок 242→241, камень 246→246 в `shots/light-mix/shore-glare-unit.png` против `split=direct`. В GUI «Post» добавлен ползунок exposure (`renderer.toneMappingExposure`) и glare strength. `?glare=0|1`, `?glareStrength= glareRadius=`. Для Cornell выключен (пресет `SceneHost.glare`), чтобы не менять пиксельные метрики существующих проверок.

Проверка: `node scripts/check-atmosphere.mjs` — старт с туманом без новых ошибок, выключение через тот же путь, что GUI, совпадает с `?fog=0` в пределах шума анимации воды/ветра, включение обратно и сдвиг камеры не дают чёрного кадра, GPU-время кадра on/off по timestamp-запросам. Кадры: `shots/atmosphere/final-*.png`, debug-листы `sheet-*.png`. Ракурс `?cam=sunward` смотрит на солнце сквозь пальмы, где виден forward-лоб.

Ограничения: нет sky/aerial-perspective LUT (у диорамы нет неба), нет многократного рассеяния помимо изотропного ambient, туман не освещён surfel GI и локальными источниками, glare — bloom-приближение без измеренного PSF. Мягкие полутени солнца (PCSS по угловому размеру 0.53°) и TAA — следующие кандидаты для «примешивания», не сделаны. Числа GPU см. `shots/atmosphere/check.json`.

### Дополнение: «листья не реагируют на свет»

Пользователь сообщил, что листья не реагируют на свет. Разбито на части и проверено по отдельности (`scripts/check-leaf-lighting.mjs`: один ракурс, солнце через новый `__audit.sun(az, el, intensity)`, средняя яркость зелёных пикселей). Диффузная и пропускающая часть BSDF реагировала: включение солнца ×1.93, противоположный азимут ×0.56. Неисправны были две другие вещи.

Первая: в сцене нет `scene.environment`, диффузный indirect даёт GI, а зеркального отражения неба не было ни у одного материала. Восковая кутикула без отражения неба выглядит матовым пластиком. `LeafNodeMaterial` теперь несёт собственный `LeafEnvironmentNode`: PMREM-radiance неба только в зеркальную часть (без IBL-irradiance, иначе диффуз считался бы дважды с GI) плюс облучённость неба с тыльной стороны для просвета, ограниченная верхней полусферой карты. Карта перед PMREM сжимается тем же коленом яркости (5→15), что и `sampleEnvEquirectClamped` в GI, иначе солнечный диск панорамы давал бы второй солнечный блик. `MeshStandardNodeMaterial.setupEnvironment` оборачивает любой `envNode` в `EnvironmentNode`, ждущий текстуру, — переопределено. Глянец кутикулы 0.22 сверху, 0.5 снизу.

Вторая: авторское солнце intensity 2 против облучённости неба HDRI ≈0.7–1.4 (`scripts/sky-balance.mjs`) — отношение 1.5–3 вместо 5–8 ясного дня; с солнцем 6 куст отвечал ×2.74. Добавлен `SceneHost.sunIntensity`: число или `'environment'`; `sunFromEnvironment.ts` интегрирует по сфере ту яркость, которую GI-колено срезает из панорамы, — это и есть облучённость аналитического солнца (для pizzo 4.66 в браузере). Beach использует `'environment'`; `?sun=<value>` переопределяет; Cornell и прочие сцены не тронуты. Итог в `shots/leaf-lighting/shrub-default.png`: солнечные листья жёлто-зелёные, теневые тёмно-зелёные с голубым отблеском неба; вкл/выкл ×2.32. Крона снизу (`leaves-default.png`) меняется слабее (×1.19): её вид определяют небо и просвет, а не отражённое солнце. Рахис использует материал листа и тоже отражает небо; это открытый вопрос. Ключ bake учитывает солнце, поэтому первый запуск beach печёт заново.

## Итерация 22 — полутени солнца по его угловому размеру

Пользователь уточнил цель «воздуха»: не среда, а то, что в жизни объекты примешиваются друг к другу — свет переносится между поверхностями, нет жёстких переходов. Первый слой этого — полутени: тень от вайи на высоте 4.5 м под солнцем с угловым диаметром 0.533° размыта на ~4 см, тень камешка у его основания резкая. Прежний фильтр (итерация 19) давал одинаковую жёсткую кромку ~1 тексель везде.

`src/shared/render/softSunShadow.ts` — PCSS поверх receiver-plane фильтра, включён по умолчанию для обычного directional солнца (`?shadowFilter=receiverPlane` — прежний жёсткий, `legacy` — PCF three). Ортографическая карта имеет линейную глубину, поэтому расстояния берутся из неё: d = Δz·(far − near). Поиск блокеров: 16 Poisson-выборок в конусе, под которым приёмник видит диск солнца (радиус d_receiver·tan(α/2), 1–16 текселей), каждая сравнивается со своей receiver-plane глубиной, чтобы наклонный пол не считал себя блокером. Полутень: радиус = (z_receiver − средний z блокеров)·(far − near)·tan α / 2 в текселях, до 16. Фильтр: при радиусе < 1.5 текселя — прежний точный сдвигаемый бокс 4×4 (без шума, исправление acne итерации 19 сохраняется); иначе 32 Poisson-выборки с поворотом по blue-noise (128×128 тайл GI, `SurfelGI.blueNoiseTexture`), каждая — билинейное сравнение 2×2 со своей плоскостной поправкой. Поправка ограничена склоном 70° на тексель расстояния, чтобы на кривых приёмниках широкое ядро не возвращало acne. Диски детерминированы (LCG dart throwing) и отсортированы по y ради кэша. Угловой диаметр — uniform `U_SUN_ANGULAR_DIAMETER_DEG`, `?sunDisc=`, ползунок «sun disc (°)» в Lighting. Существующие проходы не отключены: старый фильтр остаётся кодом и ядром нового.

Проверки: `GI_EXPECT_CLEAN=1 GI_TAG=soft node scripts/check-shadow-receivers.mjs` (Cornell) прошёл с новым фильтром — litSurfaceError 0/0, контраст настоящей тени 61.266/61.270, ошибок нет; acne не вернулось. `node scripts/check-soft-shadows.mjs` снимает `?cam=shore` с soft при диске 0.05°/0.533°/2° и с receiverPlane, меряет ширину кромки тени вайи как контраст/пиковый наклон на фиксированных строках (первая версия метрики 10–90 % ломалась на соседних листочках и была заменена), яркость освещённой стороны и GPU-мс. Результат: ширина 4.12 → 4.97 → 6.71 px при росте диска, жёсткий фильтр 4.05 px (точечное солнце совпадает с ним в пределах 2 %), освещённый песок 229.3 против 230.2, GPU-кадр 6.01 против 5.53 мс, новых ошибок нет — PASS. Тени листочков тоньше полутени, поэтому их ядро при 0.533° светлеет; это физика, а не дефект, и проверка сравнивает механизм (монотонность по диску), а не soft против hard напрямую. Кадры `shots/soft-shadows/cmp-shore-hard-vs-soft.png`, `zoom-frond-hard-vs-soft.png` просмотрены: листочки вайи размываются по расстоянию, ядро остаётся тёмным; на 2× у первой версии (nearest-выборки) виднелось зерно blue-noise; после билинейных выборок (`zoom-frond-hard-vs-soft-bilinear.png`) зерно заметно меньше, остаток виден только при увеличении.

Ограничения: один shadow map без каскадов; полутень ограничена 16 текселями (12 см при 4096 на 30 м); поиск блокеров может пропускать тонкие блокеры вне 16 выборок; без TAA остаточное зерно в широких полутенях не накапливается во времени; surfel GI по-прежнему трассирует точечное солнце, так что отскок из полутени считается от жёсткой видимости. Следующие слои «примешивания»: поднятый и цветной непрямой свет на пляже, контактная окклюзия.

## Итерация 23 — временное накопление (TAA)

Цель пользователя: пайплайн уровня «примешивания» объектов, а TAA — основа, без которой мягкие тени, окклюзия и отражения не станут чистыми. По указанию пользователя готовое из three не используется напрямую, а перечитывается и переносится к нам с улучшениями.

`src/shared/render/temporalAA.ts` — `TemporalAANode`. Обвязка по образцу three `TRAANode` (см. research-doc): узел с FRAME-обновлением, resolve на QuadMesh в RGBA16F target, копия в history, `passTexture` как выход, `RendererUtils.resetRendererState` вокруг рендера, очистка targets при сбросе. Отличия: джиттер Halton(2,3) ×8 ставится через `camera.setViewOffset` в начале кадра (`FrameGraph.beginFrame` до `gi.update` и тумана, `endFrame` после), а не в post-processing — иначе G-buffer surfel GI и туман рендерились бы без джиттера и разъезжались бы с проходом сцены; velocity получает неджиттерную проекцию (`velocity.setProjectionMatrix`). Resolve: 3×3 текущего кадра в YCoCg → mean/σ, история берётся по velocity ближайшей глубины 3×3 (дилатация), Catmull-Rom 9 выборок, клип AABB вдоль отрезка в mean ± 1.25σ (variance clipping), смешивание с весами 1/(1+luma) (Karis), история 0.9, вес падает до 0.5 при скорости 24 px, отбраковка вне экрана и при пустой истории. Вход — `rtt()` композита (после тумана и glare), так что 3×3 читаются `textureLoad`. `?aa=taa|fxaa|none`, GUI «Post»: anti-aliasing, taa history, taa clip gamma; аудит `window.__fog.aa()`. FXAA остаётся как режим.

Кадры `shots/taa/leaves-taa|fxaa|none.png`, `zoom-taa-fxaa-none.png` на `?cam=leaves` (вайи против солнца, ветер) просмотрены: кромки листьев гладкие, шлейфов на движущихся вайях нет, лёгкая мягкость против none. Счёт «ступенек» (горизонтальный скачок яркости > 48/255 в области вай): TAA 6599, FXAA 8939, без AA 12056. Ошибок консоли нет. `node scripts/check-taa.mjs`: TAA против none/fxaa по ступенькам, скачок камеры (первый кадр после — не чёрный и не старый вид), дрейф на ровном песке против none, GPU-мс.

Перенос обвязки из three дал один дефект, найденный делением: с `RendererUtils.resetRendererState/restoreRendererState` вокруг quad-рендера resolve выход был чёрным (`shots/taa/probe-plain.png`, `probe-gputime.png` — среднее 0.0), без guard — 97.3 (`probe-revert.png`), с одной лишь очисткой history при сбросе — 97.3 (`probe-clear.png`). Guard убран, очистка оставлена; причина внутри guard не разбиралась дальше.

Ограничения: нет depth-истории для disocclusion (у three есть), нет шарпенинга после накопления, история 0.9 фиксирована (без адаптации к сходимости), джиттер не учитывается в reprojection тумана (ошибка ≤ 1 px). Динамическое разрешение/TSR не делается.
